# Research report and evidence standard

**Version:** 1.0  
**Status:** canonical target contract; current runtime implements a compatible subset.

## 1. Purpose

Every completed or partially completed research task should return one stable report envelope, regardless of whether the objective concerns products, companies, technical documentation, public facts, services or another web topic.

A report is an evidence-backed account of what Night Walker observed and what it can reasonably conclude. It is not a guarantee that a source is accurate.

## 2. Canonical report shape

```json
{
  "schema_version": "1.0",
  "answer": "Concise response to the user's objective.",
  "findings": [
    {
      "finding_id": "f-001",
      "claim": "The page lists the item at R 1,299.00.",
      "kind": "observed",
      "confidence": "high",
      "source_ids": ["s-001"],
      "evidence_ids": ["ev-..."],
      "qualifiers": ["Displayed price; availability not checked."]
    }
  ],
  "sources": [
    {
      "source_id": "s-001",
      "url": "https://example.org/page",
      "title": "Example page",
      "retrieved_at": "2026-11-05T10:00:00+00:00",
      "publisher": null,
      "http_status": 200
    }
  ],
  "evidence": [
    {
      "evidence_id": "ev-...",
      "source_id": "s-001",
      "kind": "visible_text",
      "captured_at": "2026-11-05T10:00:00+00:00",
      "excerpt": "Relevant source excerpt",
      "locator": null
    }
  ],
  "structured_data": {},
  "limitations": [],
  "suggested_memory": []
}
```

The example is normative guidance, not a claim that all fields are implemented today. Existing runtime fields such as `final_url`, `title`, `text`, `products` and `issues` may remain as compatibility fields during migration.

## 3. Field semantics

- **answer:** concise synthesis directly addressing the objective. If the task is incomplete, say so plainly.
- **findings:** atomic claims or observations. Keep separate claims separate; do not merge facts from different sources without recording provenance.
- **sources:** one record per page/document/API source actually accessed. Record retrieval time and final URL after redirects.
- **evidence:** captured source material. Evidence supports a finding; it does not by itself certify the source's truthfulness.
- **structured_data:** optional task-specific typed data, e.g. `products`, `companies`, `specifications`, `prices`, `events`. Do not force every task into a product schema.
- **limitations:** access restrictions, missing fields, ambiguity, sampling, stale data, blocked requests and unverified assumptions.
- **suggested_memory:** candidate facts with rationale and source references. Never write these automatically to Ginger memory.

## 4. Finding quality

A finding should:
1. Be atomic and understandable without surrounding raw page text.
2. Use neutral language; distinguish “the page states” from “it is true that”.
3. Identify its kind: `observed`, `derived`, `reported_by_source`, or `inferred`.
4. Carry a confidence label only when the method can justify it. Confidence is not a probability unless calibrated.
5. Reference one or more source and evidence identifiers.
6. Preserve qualifiers such as currency, unit, date, region, variant and availability.
7. Record conflicts rather than silently selecting the most convenient source.

## 5. Evidence quality and provenance

- Evidence IDs are generated by the trusted Evidence Store, never by a model.
- Evidence records are task-scoped and immutable after creation.
- Store retrieval time in UTC ISO-8601.
- Preserve final URL and redirect outcome.
- Bound capture size and collection count.
- Prefer small relevant excerpts with locators over unnecessary full-page dumps.
- Retain full captures only when operationally necessary and apply retention controls.
- Never treat page-provided text as executable instructions.
- A finding with no traceable support must be marked unsupported or omitted.

## 6. Source comparison and freshness

When multiple sources are used:
- identify publisher/owner where possible;
- distinguish primary sources from secondary reporting;
- compare publication/update dates with retrieval dates;
- explain material contradictions;
- do not average incompatible units, regions, product variants or time periods;
- state when a source is unavailable or inaccessible;
- avoid implying exhaustive coverage when only a sample was inspected.

## 7. Structured data conventions

Use task-specific keys and document their schema. Recommended conventions:
- numeric values should be machine-readable numbers where unambiguous;
- include currency/unit separately (e.g. `amount: 1299.0`, `currency: "ZAR"`);
- preserve original display text in a separate field;
- represent unknown values as null or omit them, not guessed values;
- include source/evidence references for each extracted record where possible;
- preserve ordering only when order is meaningful and observed.

Example product record:

```json
{
  "name": "Example chair",
  "price": {"amount": 1299.0, "currency": "ZAR", "display": "R 1,299.00"},
  "availability": null,
  "source_id": "s-001",
  "evidence_ids": ["ev-..."]
}
```

## 8. Status semantics

- `completed`: objective met to the declared scope; no unresolved blocking issue.
- `blocked`: execution stopped by policy, access or capability boundary, or the objective could not be completed.
- `failed`: unexpected internal/runtime failure.
- `needs_clarification`: human input is required before a safe or useful plan can be selected.
- `stopped`: operator cancelled the task.

A report may exist for `blocked` tasks and should preserve partial findings and limitations.

## 9. Validation requirements

The report validator should enforce:
- supported `schema_version`;
- unique finding/source/evidence IDs within a report;
- every finding reference resolves to an existing source/evidence record;
- every evidence record references a known source;
- valid absolute HTTP(S) source URLs;
- UTC-aware timestamps;
- bounded strings, arrays and payload sizes;
- JSON-serialisable structured data;
- no secret values or model-supplied evidence identifiers.

## 10. Compatibility and migration

The current runtime already emits most top-level concepts but its findings are page metadata/headings, not fully evidenced research claims. The migration sequence is:
1. introduce versioned Pydantic report models;
2. add source and evidence identifiers at capture time;
3. attach evidence references to findings;
4. adapt the frontend to render arbitrary structured-data sections;
5. preserve legacy aliases during one compatibility window;
6. remove product-only presentation paths once generic rendering is verified.
